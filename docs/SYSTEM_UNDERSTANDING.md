# System Understanding — ZimBuild land & property platform

*Step 0 study, 2026-10-13. Read-only: no source code was changed to produce this.*

## 1. What the software is, in one paragraph

This repository contains a land-development and property ERP for **ZimBuild Properties** (Harare). Its job is to
take applicants from registration to a title deed: people apply for residential stands (with youth and other
quotas), an application passes a three-step approval, an approved applicant reserves a mapped stand, pays a deposit
and monthly instalments (USD or ZiG, by EcoCash, bank, O'mari, debit order or cash), receives SMS/WhatsApp receipts,
reminders and statements, and finally gets a CEO-signed Agreement of Sale and Title Deed once the stand is fully
paid **and** its water, sewer and roads are certified. Alongside that sit a construction-operations module (job
costing, site diaries, tenders, quality, plant) and a large set of demonstration ERP screens (leasing, HR, fleet,
supply chain, CRM, tax, permits, mortgage).

## 2. The most important fact: there are two applications in one repository

| | **A. ZHMS core** (the real system of record) | **B. "Zimbuild ERP Platform"** (demo/prototype) |
|---|---|---|
| Backend | `zhms-api/` — Node 20, Express, PostgreSQL | `server.py` — Python 3.11 standard-library HTTP server |
| Data | PostgreSQL, 10 migrations, rules enforced by triggers | **In memory** (Python objects seeded with demo data) — lost on every restart |
| Frontend | `src/` — React 18 + Vite + Leaflet (+ Tauri desktop shell) | `index.html` — one 512 KB generated HTML page (vanilla JS + Tailwind CDN) |
| Auth | Signed JWT (HS256), strict role checks | `X-User-Role` request header, **not verified** |
| Tests | 64 Node tests on a real (embedded) PostgreSQL | 149 Python tests |
| Port | 5000 (API), 1420 (client dev) | 8000 |

**A** is the application described by `README.md` (applicant registration, stand allocation, instalments). It is
the only part with durable storage, transactions, an audit chain and database-enforced business rules. **B** was
generated by an AI agent (Antigravity) from `build_full_enterprise_erp.py`; it shows many modules but keeps its data
in memory and is not connected to A's database. The two systems keep **separate stand registers** (see §6).

## 3. Who uses it (roles that exist today)

**ZHMS core (A)** — role names carried in the JWT, checked on every API route (`zhms-api/src/auth.js`). A role
grants only its own actions; ADMIN does not inherit other roles.

| Role | What they do |
|---|---|
| APPLICANT (any signed-in person) | Apply, see own stands/statements, upload proof of payment |
| LAND_OFFICER | First approval, reserve stands, create developments, import stand boundaries |
| FINANCE_MANAGER / FINANCE_CLERK | Second approval (manager), record payments, payment inbox, ZiG rates, statements, reminders |
| CEO | Final approval, sign Agreements of Sale and Title Deeds |
| ENGINEER | Certify stand servicing (water/sewer/roads); construction QC |
| AUDITOR | Verify the audit chain; read reports |
| ADMIN | Run scheduled jobs, read message log |
| PROJECT_MANAGER, QUANTITY_SURVEYOR, SITE_SUPERVISOR, QA_INSPECTOR, PLANT_MANAGER, SUBCONTRACTOR | Construction operations module |

There is **no login screen and no user/password store**: users paste a token issued by an external identity
provider (`npm run issue-token` signs one for testing).

**Prototype (B)** — 16 job roles chosen from a drop-down (ceo, portfolio, leasecrm, qs, siteops, fintax, hr, fleet,
fieldservice, dlap, planner, builder, inventory, sales, buyer, sysadmin). Anyone can pick any role.

## 5. Business rules found in the code (ZHMS core)

Configurable values live in the `app_config` table (editable without a deploy).

**Applicants**
- Age 18–50 (`min_age`, `max_age`); youth quota ≤ 35 (`youth_max_age`), checked from date of birth.
- Quota categories: GENERAL, YOUTH, WOMEN, DISABILITY, VETERAN, PUBLIC_SERVANT (non-youth quotas self-declared,
  verified by the Land Officer).
- One national ID = one person record; a self-service user can never attach an existing person's record to their
  sign-in (identity must be checked in person).
- One application in progress per person.
- Approval chain Land Officer → Finance Manager → CEO; a rejection needs a ≥ 10-character reason and returns the
  application, which restarts at the Land Officer on resubmission (round + 1). Every decision is append-only.

**Stands and allocation**
- **A stand is reserved before any money is paid**: the reservation holds the stand for `reservation_days` (7)
  while the buyer pays the deposit; unpaid reservations expire automatically (scheduled job).
- Deposit = `deposit_percent` (50 %) of the price, snapshotted with the price at reservation.
- First-come-first-served: a stand can be reserved for an application only if no **earlier approved** application
  (across all schemes) is still waiting, unless a written override reason is given.
- Quota stands (e.g. YOUTH) go only to applicants in that quota.
- **Database guarantees**: one live allocation per stand; one live stand per person (a completed deed frees the
  person to buy again); a stand that is not AVAILABLE cannot be allocated even by raw SQL; allocations are never
  deleted and their stand/person/price never change; terminal states cannot be revived.
- Stand status is derived by trigger from its allocation (AVAILABLE / RESERVED / ALLOCATED); DISPUTED and
  WITHDRAWN are set by staff only; non-buildable land (wetland, way-leave, servitude, flood zone) is always
  WITHDRAWN with price 0 and can never be booked.

**Allocation life cycle**

```
RESERVED --(deposit paid)--> AWAITING_SIGNATURE --(CEO signs Agreement of Sale; instalment plan created)--> ACTIVE
ACTIVE --(all instalments paid)--> PAID_IN_FULL --(CEO signs Title Deed; servicing 100 % certified)--> COMPLETED
RESERVED --(7 days unpaid)--> EXPIRED            (also RELEASED, CANCELLED — stand returns to the pool)
```

**Money**
- All amounts are integer cents in code; PostgreSQL `numeric(12,2)` is the source of truth.
- Every payment posts a balanced double-entry journal (channel clearing account ↔ customer stand account 2100);
  payments, journals, plans, settlements, FX rates, documents and the audit log are append-only.
- A gateway/bank reference can be credited only once (webhook retries are harmless).
- ZiG payments are converted at the latest recorded rate and refused if it is older than `fx_max_age_hours` (72);
  the ledger stays in USD. **Stand prices are USD only.**
- Instalment plan created at Agreement signing: financed = price − amount already paid; term default 12 months,
  monthly rate default 0 bps (reducing balance), optional interest-free months; the effective annual rate is
  calculated and written into the contract.

**Arrears (how they are calculated today)**
- Payments settle open instalments oldest-first; excess stays as credit.
- An instalment becomes **OVERDUE** when unpaid after `due_date + grace_days` (7); the buyer is notified once.
- Arrears for an allocation = sum still owed on OVERDUE instalments (`planPosition().overdueCents`).
- Balance = price − payments (`allocation_balances` view); outstanding = remaining instalments incl. interest.
- Reminders `reminder_days_before` (3) days before a due date; statements monthly.
- There is **no ageing (1–2 / 3+ months) bucket yet** — only overdue / not overdue.

**Title**
- A deed is issued only for a PAID_IN_FULL allocation on a stand whose water, sewer and roads are CERTIFIED
  (database trigger); full certification needs the council certificate reference.

## 6. Data held today

Local database (`localhost:5432`, PostgreSQL 18 on Windows, **no PostGIS available**): only reference and demo data.

| Table | Rows |
|---|---|
| developments | 3 (Budiriro Phase 2 Youth Scheme, Midlands 3500, Matabeleland North 700) |
| la_spatial_unit (stands) | 8 (7 AVAILABLE, 1 WITHDRAWN wetland), all with WGS84 boundaries |
| app_config / ledger_accounts / quota_categories | 11 / 6 / 6 (reference data) |
| la_party, applications, allocations, payments, construction tables | **0** |

Migrations applied: 001, 003–008, 010. Migrations **002 and 009 (PostGIS geometry) were skipped** because PostGIS
is not installed (`ZHMS_SPATIAL=0`). No real personal data exists in the database, so nothing can be lost by
migrations today.

**Stand registers that exist in parallel** (they do not synchronise):
1. PostgreSQL `la_spatial_unit` (ZHMS core) — the guarded, audited one.
2. A hard-coded `standsData` array inside `index.html` (prototype) — browser memory, resets on reload.
3. Python `server.py` in-memory registers (`/api/allocations/register`, `LandSalesManager`) with hard-coded buyers.
4. Unused schema definitions: `src/real_estate_erp/schema.sql`, `schema.prisma` and SQLAlchemy `models.py`
   (`land_parcels`, `real_estate_units`, …) and `spatial/schema.sql` (`la_party`, …) — never connected to a database.

## 7. What works, what is broken, what is half-built (observed 2026-10-12/13)

**Works (verified by running)**
- ZHMS API: all 64 tests pass on a real PostgreSQL (lifecycle, double allocation under 50 concurrent requests,
  instalments, webhooks, GIS import, security, construction).
- Python prototype: 149 tests pass; all 25 tabs render; the System Check reports 22/22 modules online.
- React client type-checks; when it was last reachable, the construction workspace and the map ran against the
  live API.

**Broken**
- React client is unreachable (entry page replaced — §4).
- Production layout does not line up: nginx serves the React build at `/` and the Python API at `/api/erp/`, but the
  prototype page calls `/api/...` and the React CRM tab calls `ERP_BASE/api/crm/...`; the Python Docker image would
  fail at start because `requirements.txt` lacks SQLAlchemy.
- About a dozen prototype buttons report success without the server saving anything (HR onboarding, attendance,
  payroll, fleet logs, field service, youth registration, material dispatch, offline sync).

**Half-built / placeholder**
- Utility infrastructure overlay draws three fixed lines around each development centre labelled
  "OPERATIONAL/ENERGIZED" — not real data.
- SG coordinate schedule conversion uses a flat approximation, not a survey projection.
- "Redis job queue": Redis is in Docker Compose but nothing connects to it; jobs run in an in-memory thread pool.
- `src/real_estate_erp` (FastAPI app, SQLAlchemy/Prisma models) is not mounted or connected to a database.
- React Supply Chain tab is a static mock-up.
